# Architecture

Read before touching routing, the `app/` ↔ `lib/` ↔ `components/` split, auth, or session handling.

## The view lives in the URL path, not a query param (2026-08-20)

`app/page.tsx` redirects `/` to `/month`; `app/[view]/page.tsx` accepts exactly `month | week | day | year | list | stats` and 404s on anything else. It calls `generateStaticParams()` so each view gets a pre-rendered static shell and the app opens straight into the right view with no flash of another one. Decided in `afeca9a` ("cleaner URLs and server-side static rendering"). **Revised 2026-11-26**: the root layout's `generateMetadata` reads the request headers (absolute `og:image`, `deployment.md`), so every view now renders per request (`ƒ` in the build) instead of from a build-time shell. The path still names the view, so it still opens with no flash of another one; the cost is one cheap server render per page load. `generateStaticParams` stays as the list of valid views. **How to apply**: adding a view means adding it to *both* `VIEWS` in `app/[view]/page.tsx` and `ViewMode` in `lib/dates.ts` — they are two hand-kept lists of the same set.

Everything else that is user-visible state (anchor date, filters) is serialised into the *query string* by `lib/urlState.ts`, which omits any value sitting at its default. Keep that property: it is what makes shared links short and the back button meaningful.

## Server holds the secrets, client holds the library (2026-08-20)

The Spotify client secret and the OAuth tokens never leave the server: tokens are httpOnly cookies (`lib/auth.ts`), and every Spotify call goes through a route under `app/api/`. The *library itself*, by contrast, is fetched page by page by the browser and cached client-side (see `data-and-sync.md`). So `app/api/*` routes are thin: resolve a token, call `lib/spotify.ts`, map errors. Business logic that does not need a secret belongs in `lib/` as a pure function (`lib/library.ts` filters, `lib/dates.ts`, `lib/urlState.ts`) so it stays testable and usable from both sides.

Every API route sets `export const dynamic = "force-dynamic"` and a `maxDuration` budget (30s for album/track pages, 15s for player control). Those budgets are load-bearing: the client's page size is tuned against them.

## Security headers come from one list, and the policy is report-only (2026-10-19)

**Decision** (the portfolio standard, C16, a `page` rule): `lib/security.ts` is the one list — HSTS, `nosniff`, a referrer policy, `X-Frame-Options: DENY`, a permissions policy and a `Content-Security-Policy-Report-Only` — and `next.config.ts` applies it to every path through `headers()`, so the standalone server the Home Lab image runs sends it with no proxy in front; `tests/security.test.ts` holds the list to what the app loads and the config to the list (by text: Next's own loader is what resolves `next.config.ts`, so a test cannot import it). The policy allows exactly what the pages load: this origin; inline scripts and styles (`'unsafe-inline'` — Next's hydration and the panel bootstrap in `app/layout.tsx`; a nonce through a `proxy.ts` is the way to drop it); Spotify's four album-art hosts in `img-src`, which are also, from the same constant, `next/image`'s `remotePatterns` (`SPOTIFY_IMAGE_HOSTS`) — covers are plain `<img>` tags from those hosts; `connect-src 'self'` because the browser only ever calls `/api/*`; `'unsafe-eval'` in development only, for React's stack rebuilding. **Why report-only**: it blocks nothing and lists in the browser console what an enforced policy would have blocked; a wrong directive enforced blind would break the mini-player or the covers on the Home Lab with nobody watching. **How to apply**: a new origin the browser loads from (a font, an API, an image host) lands in `lib/security.ts` and its test in the same commit, never in `next.config.ts` by hand; the header is renamed `Content-Security-Policy` in `security.ts` and its test, nothing else, once a tour of the Home Lab instance — every view, a sync, the mini-player, an install — comes back with a clean console (MEMORY.md, open items). `next.config.ts` replaced `next.config.mjs` so it can import the list typed.

## Two React context providers wrap the whole app (2026-08-20)

`app/layout.tsx` mounts `SyncProvider` (library data + sync job state) and `PlaybackProvider` (player state) around everything. Components read them by hook rather than by prop-drilling. `SyncProvider` hydrates **asynchronously** on purpose — it reads IndexedDB, and doing that synchronously blocked the initial render (`afeca9a`). **How to apply**: never assume the library is present on first paint; components must render an empty/loading state without crashing.

## Scope drift is a first-class failure mode (2026-08-20, rev. 2026-10-19)

Playback scopes were added after the first users had already authorised the app, so their refresh tokens were minted without them. The refresh response echoes the scopes the *refresh token* carries, which is why `resolveAccessToken()` returns `scope` and `lib/playerErrors.ts` exposes `scopeGuard()`: a player route whose required scope is known-missing short-circuits with `reauth_required` instead of calling Spotify, getting a 401 and triggering an endless refresh loop. An **empty** granted-scope string means "unknown" (session predates scope tracking) and deliberately never blocks. **How to apply**: any new endpoint needing a new scope must add it to `config.scopes` *and* guard with `scopeGuard()`, or existing sessions will 401-loop.

The `[SYNC-DEBUG]` instrumentation that investigation left in `lib/spotify.ts` (every `apiGet` result with its timing, each token refresh with its granted scope string) prints only with `SYNC_DEBUG=1` (`lib/debug.ts`, since 2026-10-19): a production console carries neither every call nor the scopes by default — a log line per Spotify request is noise, and the scope string is session detail nobody asked to be logged. **How to apply**: new instrumentation goes through `debug()`, never a bare `console.log`; to look at the scopes on the Home Lab, set the variable in its `.env`, restart, read, unset.

## Errors are mapped once, centrally (2026-08-20)

`lib/playerErrors.ts:mapPlayerError()` is the single place that turns a thrown Spotify error into a response (401 re-auth, 403 Premium required, 404 no active device, 429 back-off). A 403 on a *read* endpoint means "not a Premium account", not "forbidden" — before that was handled, `/api/player` returned a raw 502 to the browser every 5 seconds forever for non-Premium users. **How to apply**: throw typed errors with a `.status` from `lib/spotify.ts`; do not build ad-hoc error responses in a route.

## Sésame is a gate in front, the Spotify sign-in stays behind it (2026-11-16)

**Decision**: the owner wants his internal tools behind his Sésame (OpenID Connect, passkeys). This app had **no gate at all** — its only sign-in is Spotify's OAuth, which says whose library to show, not who may use the instance — so Sésame is added in FRONT, in `proxy.ts`, and the Spotify flow is untouched behind it. With `SESAME_ISSUER`, `SESAME_CLIENT_ID`, `SESAME_CLIENT_SECRET` set, a visit without the gate cookie (`sc_gate`, 30 days) goes straight to `/api/auth/sesame/login` (no extra page: silent when Sésame's session is open), and an API call gets 401 `sign in through Sésame`; empty, or in demo mode, nothing changes. Both cookies (`sc_gate`, and `sc_sesame` for the round trip's state and PKCE verifier) are HMAC-SHA256 with a key derived from the client secret per purpose — no new secret, and one can never pass for the other; Web Crypto, so the same code runs in `proxy.ts` and in a route (`lib/sesameGate.ts`, tested). The protocol is openid-client's. **Why a gate and not native per-user Sésame**: the per-user identity is already Spotify's (`sp_uid`), and Sésame only needs to say "allowed here". **Why not Cloudflare Access**: one gate per app, no double sign-in, the owner's choice. **How to apply**: a new public path (a webhook, a callback) goes in `gatePublic` with its reason; a static file fetched without a session (icons, manifest, `og-image.png`, `sw.js`, `offline.html`, `robots.txt`) goes in the matcher's exclusions instead, and `tests/pwa.test.ts` checks the matcher both ways. The instance itself is `noindex` (metadata + `public/robots.txt` `Disallow: /`); the showcase is the public page.
