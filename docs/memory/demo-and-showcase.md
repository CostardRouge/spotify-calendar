# Demo mode & the GitHub Pages showcase

Read before touching `DEMO_MODE`, `lib/demo.ts`, `lib/demo-library.json`, `showcase/`, `scripts/`, or `.github/workflows/pages.yml`.

## Demo mode is a product feature, not a test fixture (2026-08-20)

`DEMO_MODE=1` makes every API route serve a fixture library and require no authentication — including `/api/auth/login`, which redirects straight to `/month` so the "Connect" button works. It exists for two reasons at once (`e32cd43`): anyone can run `DEMO_MODE=1 npm run dev` and poke at the UI without creating a Spotify app, and the Pages workflow can boot the app headlessly to take **real** screenshots of the real UI rather than mock-ups.

**How to apply**: a new route that calls Spotify must handle `isDemo()` too, or it 401s in the showcase build and the screenshot shows an error state. `demoPage()` and `demoGenres()` return the same shapes as the Spotify-backed helpers, so the demo branch stays a one-liner at the top of the route.

## The fixture library is real releases with synthetic dates (2026-08-20)

`lib/demo-library.json` is generated by `node scripts/build-demo-library.mjs` and holds real albums, tracks, artists and cover-art URLs; only the save-dates are invented, so the calendar looks plausible. Items ship pre-genred, which is why `demoGenres()` resolves from the fixtures instead of calling anything. **How to apply**: edit the seed lists in the script and regenerate — do not hand-edit the JSON.

## Screenshots are captured against a running app (2026-08-20)

`.github/workflows/pages.yml` on every push to `main`: `npm ci` → install Playwright chromium → `npm run build` → start with `DEMO_MODE=1` → poll `/api/health` until it answers → `node scripts/showcase-screenshots.mjs site/screenshots` → copy `showcase/index.html`, `showcase/llms.txt`, `public/og-image.png` and the whole `public/icons/` (the app's icon set, which the showcase's head links to relatively — `frontend.md`) into `site/` → deploy.

Consequences worth knowing:

- `site/` is **generated and gitignored**. Edit `showcase/index.html` and the script; never `site/`.
- Screenshots regenerate on every deploy, so anything visible in the app (titles, layout) propagates to the showcase automatically — and a stale name in the app shows up in the screenshots, which is exactly how `f58f99b` was noticed.
- The script waits for every visible `<img>` to settle, then pauses 400 ms for lazy decodes, and captures anyway on timeout rather than failing the build.
- `FAKE_COVERS=1` replaces the album-art CDN with generated placeholders for offline or sandboxed local runs. CI leaves it unset and loads real art. Never commit screenshots taken with it.
- One-time repo setup, not reproducible from code: **Settings → Pages → Source: "GitHub Actions"**.

## The showcase is a public page, and is treated as one (2026-10-19)

**Decision** (the portfolio standard, C17): `showcase/index.html` carries a meta description, a canonical address (`https://costardrouge.github.io/spotify-calendar/`), OpenGraph and Twitter tags whose image is the app's own 1200 × 630 card (`public/og-image.png`, copied beside the page by `pages.yml` and named by its absolute address, as previews need — not a screenshot), the app's icon set (`frontend.md`) and a legal notice whose facts are copied from Versus's and spotify-poller's notices: publisher Steeve Pommier, a private individual; host GitHub Pages (GitHub, Inc.'s address); no measurement at all — the page loads no tracker, no script and no third-party resource, which is the fact the notice states and `tests/showcase.test.ts` keeps true (no `<script`, no remote `src`, no remote stylesheet, one `h1`, the card's size); MIT. The app itself is not a public page: it sits behind Spotify's OAuth on whoever's machine runs it, so it carries no notice and no measurement. **Not done, by choice for now**: a French twin of the page (N4 asks for English and French on a public page; the showcase is English only, like spotify-poller's, and an exception is not written in `CLAUDE.md` because none was decided — the owner's call), and Umami (R: the notice would then have to list what is sent). **How to apply**: a tracker, a font or a script added to the page changes the notice and the test in the same commit; a renamed `og-image.png` breaks the preview silently — the test reads the file by name.

## `llms.txt` is a tracked file beside the page, held to it by a test (2026-10-22)

**Decision** (C17, attribute J2 of the portfolio standard): `showcase/llms.txt`, in the llmstxt.org shape, is copied to the showcase's root by `pages.yml` (GitHub Pages serves it as `text/plain`), linked from nothing, with no robots.txt or sitemap to list it in — the showcase has neither. It is **hand-written** rather than generated: the showcase has no build step or config the page itself is drawn from (one static HTML file), so a generator would only move the prose into a script. Its facts are the README's and the page's, nothing else. `tests/showcase.test.ts` holds it to the page: one H1 and a summary, every address it names is the showcase, an anchor the page carries (`#legal`), or a GitHub address the page itself links to, and the workflow's `cp` line exists. **How to apply**: a renamed anchor, a link dropped from the page or a new address in `llms.txt` fails the test — change both together; a new fact about the app (a view, a deploy path) goes into the README first, then here.
